# Module reference

`records.ts` defines strict runtime schemas, immutable operation IDs and canonical content revisions. A record belongs to the public key of its signed tree. A case has one owner. Collaborators contribute evidence referencing an owner's request; they do not edit that owner's tree. A case may declare up to eight structured information needs, each with a stable ID and canonical question. Requests must identify a declared need; Relay binds its canonical question and ID to the request. The request stays pending until a linked response is read and cited in the saved brief. A save is refused if a declared need remains unanswered, even if the model reports an empty missing-information list. Free-text-only tasks do not provide deterministic semantic coverage for required missing information.

`store.ts` opens one local writable Hyperbee2 tree and separate remote read-only trees on Corestore sessions. Pairing persists public keys. TCP carries actual Corestore replication streams. Remote refresh updates the visible tree root. Reads enforce deadlines and payload limits. A write queue serializes local effects and verifies an expected case fingerprint before accepting a brief.

`retrieval.ts` derives rebuildable passages from accepted evidence with source IDs, revisions and exact UTF-16 offsets. It preserves original text, covers long records and uses a deterministic BM25-like lexical score to select up to twelve passages. No-overlap queries return no matches; exact source IDs retrieve that source's passages. `context.ts` protects instructions, the task, outstanding questions and required contributions within a default 7000 estimated-token budget. Optional rerankers reorder the lexical candidate pool before admission. A protected availability summary says how many passages were omitted. It cannot guarantee that the generator will search for them.

Recent assistant calls and their results are kept as complete groups. If necessary, context drops the oldest resolved group while preserving the latest complete group and mandatory application state. It never keeps a tool result without its call. An oversized latest group fails explicitly unless it qualifies for the rejected-draft exception below; required state always remains protected. The budget uses UTF-8 JSON bytes plus a template allowance as a conservative token estimate, not an exact generator tokenizer.

Fresh source IDs read during the current run remain in protected `readIds` after protocol compaction. These IDs mean some excerpt was delivered, not that the whole record was read. The exact delivered excerpts remain in the trusted citation cache. Required source passages remain protected separately. When a retained read result covers a required passage exactly at the same revision, the index omits duplicate text and references the result by `textInToolResult`. If that group is later dropped, the index text returns. If a needed quotation is absent from the current prompt, another page read can still be necessary. The consolidated `readProgressGuidance` encourages saving once all required sources have delivered excerpts; it does not claim full-source coverage or prescribe calls. Restart reconstructs application progress from records and requires new citation reads.

Under budget pressure, an explicitly rejected save draft can also leave context as a whole resolved call/result group. This exception requires concrete retained feedback and a validation failure with no committed brief. Unresolved calls, successful effects and infrastructure failures do not qualify. When retained failed tool feedback exactly matches the protected feedback, context references its call with `feedbackInToolResult` instead of duplicating the text. If that group leaves context, the feedback text is restored. Repairs rebuild from trusted store data and read progress; repair counts and equivalent-failure detection are unchanged. The trusted system guidance is 1040 characters, reduced from 1125 to leave room in the same budget.

`minilm.ts` uses an explicitly prepared, hash-verified INT8 ONNX cross-encoder through Transformers.js. Inference is local-only. Cancellation waits cooperatively for any running ONNX batch. `laya.ts` submits full individual passage states in batches for three-class decisions, preserves lexical order on ties, and supports candidate and option-order probes. Neither confidence nor `actProbability` authorizes actions. Selector errors or truncation fall back visibly only after successful cleanup; cleanup failure stops the run and quarantines the runtime.

The generator is released before a native selector runs, keeping their heavy work sequential. The trusted pure lexical implementation does not unload it on a query refresh. The generator still unloads after each agent run. Checkpoint timestamps have an owned-record logical lower bound, so a host-clock rollback across restart does not make new progress older than prior local progress. Ordering compares parsed instants, including accepted offset-form timestamps. This is local ordering, not clock synchronization or distributed consensus.

`qvac.ts` adapts native SDK responses to the harness model interface. It preserves assistant tool calls and tool result IDs. Loading and decode use targeted cancellation, and the generator unloads after a run. Peer status exposes `cleanupError` when runtime cleanup failed.

`agent.ts` owns the model-to-tool-to-result loop. `find_evidence` returns navigation metadata, not source text, with `skip`, `limit` and `nextSkip`. The native `read_record` schema exposes source ID and UTF-16 offset. Trusted code returns exact pages of up to 1000 characters with `nextOffset`; the library validator retains optional length for controlled callers. `tool-budget.ts` tests the projected next protected context, including future offered tool schemas and JSON-escaped protocol, before delivering results. Search rows are reduced with a correct cursor and reads are shortened to exact pages when needed. At the default context size, ordinary result bodies share a soft 1000-byte allowance; a single required read may exceed it when the full requested page fits after duplicate index text is removed. The default 7000 estimated-token budget and 1000-character page limit remain unchanged. Known-ID recency prediction follows the normal next turn and stale read-cache entries are purged. Future peer changes or tool errors can still cause explicit overflow.

Quote validation checks delivered excerpts separately, so a quote cannot bridge an unread gap. Code owns schemas, permissions, acceptance and state transitions. A failed proposal receives specific feedback; committed requests remain. Repeated equivalent failures, attempt limits, native failures, overflow and cancellation stop work. Call attempts are checkpointed before inference so a crash cannot reset the budget.

Accepted briefs use factPolicy quoted-observations-v1. Trusted code turns each validated source quotation into a fact with the same text and one reference. `brief-input.ts` exposes the native save input as `{ quotes: { sourceID: "exact quote" }, uncertainty: [], missing: [] }`. Quote keys are limited to read IDs, required source keys are required, and the map holds 1 to 32 entries of at most 1000 characters each. Its strict parser compiles each key and quote into one fact. The native interface permits one contiguous quote per source; the legacy facts input remains available for controlled library and replay fixtures, including multiple noncontiguous quotes, but is not offered to the native model. Coverage, exact delivered text and current revisions are checked independently, so the schema cannot guarantee valid model output. Legacy draft prose is retained only as a labelled unverified interpretation in uncertainty. Every new brief includes a trusted root-cause uncertainty notice. This separates reported observations from model explanations without claiming to verify the truth of a source or the entailment of a hypothesis. Earlier immutable briefs without this policy are legacy records.

`resume.ts` scans owned pending or interrupted cases. A remote evidence record matters when it references an outstanding request and its contribution ID has not been consumed. Child run IDs derive from persisted prior work and contribution IDs. Checkpoints carry consumed IDs and cumulative budgets. Recovery can settle an already committed brief without reexecuting its write. Completed, cancelled and failed runs do not automatically restart.

`cli.ts` hosts a peer and a loopback control API. Other CLI invocations read only that peer's control metadata and submit authenticated commands. The live demo starts separate processes and directories. Its coordinator waits for a terminal run to settle and records cleanup status before asserting success or failure; it never opens peer core files.

`control-client.ts` supplies the shared CLI/demo JSON transport. Its 720-second wall-clock deadline covers delayed headers and the full response, while the agent retains its separate ten-minute work limit. It bounds response bytes and closes requests on timeout or cancellation. It never performs inference or changes peer state except through the existing authenticated commands.

`retrieval-eval.ts` evaluates nine frozen version 2 synthetic cases with disjoint development and held-out families. Grader-only spans are not forced into context. `eval.ts` runs synthetic cases through the same Agent and real temporary stores. Replay is a scripted model fixture that inspects protocol and tool results. Live evaluation uses QVAC. State checks grade persisted outcomes. Comparison validates identities and configuration before calculating deltas.

`retrieval-regrade.ts` recomputes span checks from recorded selections without inference. `recorded-ranking.ts` reapplies captured MiniLM logits and Laya classes to the current context budget. It validates the historical configuration and requires explicit source attribution when the raw report lacks Git metadata. Query identity is inferred from the frozen fixture and historical harness, not authenticated by a captured query field. This replay measures current budgeting of recorded predictions, not a new native evaluation.

## Request flow

1. A owns a case and evidence. Its model reads the evidence and writes a question and pending brief. When no source has been read, ordinary completion after a persisted unanswered request may instead checkpoint pending work without a brief. This accepts no observations. Malformed or length-limited output still fails through bounded corrective feedback, and cancellation is checked after the awaited request scan.
2. B replicates the question, then can remain connected or continue while A is offline.
3. B writes evidence in B's tree with the request ID.
4. A reconnects and replicates B's blocks. The resumer recognizes an unconsumed contribution.
5. A refreshes context and starts bounded work with that contribution protected. A valid new brief cites the contribution and a terminal checkpoint records consumption.

The [2f23582 long-record development run](../artifacts/passage-demo-2f23582.json) completed this flow once with the deterministic selector, including late exact quotations, cleanup and restart deduplication. It does not establish a success rate or a current two-peer pass for either optional selector.

This flow depends on locally received blocks. It cannot prove all peers have supplied their latest data. Source quotations support inspection; semantic truth remains a limitation of the model and the evidence.
